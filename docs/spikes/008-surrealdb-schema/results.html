Spike 008 Results: SurrealDB Read Model

This document is the implementation handoff for the Zeko explorer SurrealDB schema. It answers the questions in the spike README and names the concrete files, tables, indexes, graph edges, query files, and verification commands the implementer should use.

Status: ready for implementation review
Target: SurrealDB v3
Schema owner: SurrealKit
Scale proof: 100k persisted gate passed

Decision

Build the explorer read model as a schemafull SurrealDB v3 database managed by SurrealKit. The model uses canonical records for source-of-truth state, enforced graph relation tables where relationships carry metadata, native full-text search indexes, complete keyset cursor tuples, and a SurrealDB table view for the minute-level transaction aggregate.

20domain tables and relation/view tables
45query files with EXPLAIN comments
30Cucumber scenarios passing
26/26100k benchmark paths passing
Important model constraint: there are no manually maintained feed tables, search-document tables, bridge quality queue tables, or mutable network-stats projection tables in the accepted schema. If a future change proposes one, it needs an EXPLAIN plan and benchmark evidence proving the native SurrealDB shape cannot meet the budget.

Record IDs and Natural Keys

GraphQL resolvers should treat SurrealDB record IDs as the internal node identity and encode them into Relay global IDs. Natural blockchain identifiers remain unique secondary indexes, not ad hoc alternate tables.

Stable identitiesEntity rows carry stable IDs assigned by the indexer. The schema also stores natural fields such as hash, public_key, after_state, and aux for unique lookups.
Natural uniquenesstransaction.hash, account.public_key, bridge_operation(aux, aux_sequence), outer_action.after_state, inner_action.after_state, and zkapp_action.action_state are unique indexes.
Pagination keysNewest-first resolver order is implemented with negative sort fields such as sort_block_height. Cursor predicates include the full sort tuple.
Rollback keysRollback-sensitive child rows carry target_ledger_hash and have indexes so the indexer can find and remove affected rows without replaying the whole database.

Do not implement pagination with broad tuple OR predicates or descending raw-height scans. Use the query files as resolver templates.

Relation tables are ENFORCED. Cleanup events delete relation rows when either side is deleted, so rollback and reindex paths have deterministic edge behavior.

Time-Series and Aggregates

Network status is derived from canonical tables. Current totals use SurrealDB COUNT indexes. Recent throughput uses the declarative transaction_minute_stats table view because raw 24-hour grouping over canonical transactions exceeded the dashboard budget at 100k rows.

Current countsnetwork-stats-current.surql reads canonical tables and COUNT indexes. There is no mutable singleton stats table.
Throughput charttransaction_minute_stats is maintained by SurrealDB from canonical transaction rows and indexed by minute.
Future bridge evidence historyIf product needs detected/resolved reason history, model it as canonical bridge evidence time-series data first, not as an operator queue projection.

Schema and Migration Workflow

SurrealKit is the schema management tool for this spike. Application startup should not be responsible for applying ad hoc DDL.

  1. For disposable development databases, run surrealkit sync from spikes/008-surrealdb-schema/surrealkit.
  2. For production-like environments, use SurrealKit rollout planning, rollout start, and rollout complete.
  3. Use the representative migrations under surrealkit/migrations as the pattern for data-preserving schema changes and backfills.
  4. Treat REBUILD INDEX, large backfills, and table-view rebuilds as explicit migration steps for existing production data.
  5. Use Surreal Sync only for supported external import/CDC sources such as PostgreSQL archives, JSONL snapshots, or a Kafka bridge. It is not a replacement for the NATS-backed indexer unless the source is actually supported.

Implementation Notes

Indexer writes

  • Write canonical rows first, then create relation rows with RELATE or relation-table inserts.
  • Populate compact scalar connection keys such as sender_public_key, receiver_public_key, account_public_key, and negative sort_* fields at ingest time.
  • Maintain bridge_operation.data_quality and data_quality_reasons in TypeScript from explicit source evidence. SurrealDB events do not classify bridge quality.
  • On rollback, use target_ledger_hash indexes to find affected transactions, account activity, inner actions, zkApp events, and zkApp actions.

GraphQL resolvers

  • Use the committed query files as resolver templates. Keep cursor arguments as full tuples.
  • Use relation-table feed indexes for account-local feeds. Use graph traversal for bounded detail pages.
  • Do not decode zkApp raw fields in the explorer database. Compose labels from the contract registry API.
  • Use shared live-query workers in the API process and fan out to SSE clients.
