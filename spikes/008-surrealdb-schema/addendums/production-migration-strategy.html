Production Migration Strategy

Operational rollout model for SurrealKit migrations across isolated Zeko explorer stacks while production stays live.

Spike 008 addendum SurrealKit rollouts One stack per network
Results SurrealKit Project Migration Feature

Decision

Use SurrealKit rollouts for every shared or live database.

Use surrealkit sync only for local, CI, preview, and disposable databases where the database can be reconciled directly to desired state.

The indexer and APIs must not apply DDL on startup. Schema changes are a deploy step, visible in Git, run once per target stack, and promoted with the same reviewed rollout artifact from lower environments to mainnet.

Promotion Order

  1. Local: use surrealkit sync, run Cucumber, schema validation, and benchmark smoke tests.
  2. Lower live stack: run the rollout against zeko-m-devnet or the team's current testnet stack.
  3. Pre-mainnet: promote the same rollout artifact to zeko-m-alphanet.
  4. Production: promote the same rollout artifact to zeko-m-mainnet.

Do not regenerate the rollout between stacks. Each network has its own SurrealDB instance, so each stack runs and records the rollout independently.

Runbook

# one time per existing shared database
surrealkit rollout baseline

# per schema change, from the reviewed desired-state schema
surrealkit rollout plan --name <change_name>
surrealkit rollout lint <rollout_id>

# per target network
surrealkit rollout status
surrealkit rollout start <rollout_id>
# deploy compatible indexer/API
# run smoke checks
surrealkit rollout complete <rollout_id>

start is the expansion phase: additive tables, fields, indexes, and compatible backfills. complete is the contract phase: destructive cleanup only after all running code no longer depends on the old shape.

Compatibility Rules

Add firstNew tables, optional fields, indexes, and relation tables land before code depends on them.
Dual-read or dual-write when neededRenames and shape changes ship through compatibility windows, not single-step destructive changes.
Backfill explicitlyData-bearing changes, REBUILD INDEX, and large updates are named rollout steps with progress and smoke checks.
Contract lastDrops, required-field tightening, and old-index removal wait until the new code has passed on the target stack.

Deployment Shape

ConcernRule
ExecutionRun migrations as Kubernetes Jobs in the setup phase, before API and indexer rollout.
GitOpsUse versioned or release-hash job names so Flux can re-run a migration intentionally for each release.
OrderingNATS and SurrealDB must be healthy first; setup jobs must pass before data-plane workloads are marked healthy.
SecretsInject DATABASE_HOST, DATABASE_NAMESPACE, DATABASE_NAME, DATABASE_USER, and DATABASE_PASSWORD from the target network secret.
AuditUse SurrealKit rollout metadata as the migration ledger instead of inventing an app-level table.

Rollback Posture

Use surrealkit rollout rollback <rollout_id> only while a rollout is still in flight and before contract/destructive completion. After completion, treat the explorer database as a rebuildable read model.

No down-migration dependency.

If a completed production schema change is wrong, stop the bad code, restore from SurrealDB export if appropriate, or rebuild SurrealDB from NATS JetStream and R2 snapshots. NATS remains the source of truth.

Evidence

  • PRD.md defines full stack isolation per network, including separate SurrealDB instances.
  • PRD.md assigns schema sync, rollouts, seeding, and declarative tests to SurrealKit.
  • Flux deployment topology already models SurrealDB migration as a setup Job with health-gated dependencies.
  • Spike 008 migration coverage proves migration 0002 preserves an existing bridge row and backfills sort_submit_block_height.
  • SurrealKit's workflow distinguishes direct sync from staged migration workflows for shared and production databases.
