Scale Boundary

Current local evidence is not a 100x/1000x proof. The local benchmark proves query shape and catches obvious index mistakes. It does not prove behavior at 20M, 200M, or 2B rows.

The persisted Docker benchmark now uses a SurrealQL import file and surreal import, not row-by-row HTTP seeding. A 2,200,000-transaction import file was generated successfully, but importing it into persisted SurrealKV under the local Docker resource limit was killed with exit code 137 after writing roughly 11.8 GB to the volume. That is a real scale blocker, not a passing benchmark.

Does a larger dataset require more RAM?

Yes for the current benchmark command, because it starts SurrealDB with the memory backend. With memory, records and indexes live in process memory, so row count and index count directly increase RAM pressure. That is useful for fast tests, but it is not a production deployment model.

Would Docker solve the in-memory issue?

No. Docker is only packaging/isolation. surreal start memory inside Docker is still in-memory. Docker can make a persistent benchmark reproducible if it runs SurrealDB with a persisted storage engine and mounted volume, but Docker itself does not change memory behavior.

What must happen outside this spike?

Run 20M, 200M, and 2B-row benchmarks against the pinned production SurrealDB version using persisted storage, production-like memory limits, and bulk import/snapshot seeding. The local Docker run proved the benchmark harness shape, but the local Docker memory/disk budget is not enough to claim testnet-plus scale.

Bridge Data Quality Contract

Decision: bridge_operation.data_quality is a denormalized summary maintained by the TypeScript indexer. The detailed source of truth for non-complete evidence is bridge_quality_issue, one row per open reason.
Exact field definitions

type is the bridge direction: deposit or withdrawal. status is the current bridge lifecycle state, such as submitted, l1_witnessed, committed, completed, cancelled, or rolled_back.

data_quality_reasons is the ordered list of currently open bridge_quality_issue.reason values for that bridge operation. It is a denormalized convenience field on bridge_operation; the detailed records live in bridge_quality_issue.

Maintenance algorithm
  1. The TypeScript indexer owns data_quality. Operators do not edit it manually, and SurrealDB events do not compute it.
  2. On each bridge-affecting message, the indexer upserts the concrete bridge_operation fields proven by that message.
  3. The indexer evaluates the required-evidence matrix for the row's current type/status.
  4. For every missing or inferred evidence item, the indexer upserts one bridge_quality_issue row keyed by (bridge_operation, reason).
  5. For every previously open issue that is now satisfied, the indexer sets bridge_quality_issue.resolved_at.
  6. The denormalized summary is recomputed from open issue rows: no open issues means complete; otherwise unrecoverable wins over inferred, which wins over partial.
  7. data_quality_reasons becomes the ordered list of open issue reasons.

Index Plan

Every open-ended GraphQL Connection has an index matching its filter prefix and sort key. The benchmark-driven correction is that newest-first high-volume feeds should not rely on descending scans or large tuple OR predicates. The indexer computes the negative sort-key fields at ingest time.

Graph Model

SurrealDB graph relations are used where the edge has semantic metadata or where detail pages need bounded traversal. Connections use composite indexes; detail views use graph traversal.

account_transactionPreserves sender, receiver, fee-payer, and touched-account roles without flattening multi-account transactions into duplicated transaction rows.
batch_transactionBatch detail can traverse contained transactions in bounded pages while transaction feeds still use composite indexes.
l1_action_linkModels witness and commit roles explicitly because one commit action can cover multiple bridge operations.
l2_action_linkKeeps INNER_PK action evidence attached to the bridge operation with a role instead of encoding it as optional columns only.
bridge_transaction_linkSeparates user-facing transaction detail links from action-chain evidence links.

Migration Strategy

The spike includes a data-bearing migration proof. 0001_initial_core.surql creates a representative pre-spike-006 core schema. 0002_l1_watcher_and_bridge_quality.surql adds bridge data quality, the bridge sort key, L1 watcher cursors, and published-message idempotency.

The Cucumber scenario applies migration 0001, inserts an existing bridge operation, applies migration 0002, and verifies the row survives with data_quality = "complete". Migration 0002 also backfills sort_submit_block_height = 0 - submit_block_height, proving the strategy for adding benchmark-driven sort keys to existing data.

  1. Fresh environments
    Apply schema.surql as the consolidated current schema for test and development databases.
  2. Production rollout
    Apply numbered forward-only migrations before deploying the indexer/API that writes the new fields.
  3. Audit trail
    Record applied versions in schema_migration so repeated deploys are idempotent.
  4. Rollback posture
    Do not rely on down migrations for the read model; rebuild SurrealDB from NATS/R2 snapshots when rollback is required.
  5. Large table changes
    Treat REBUILD INDEX and backfill jobs as explicit migration steps for existing production-scale tables.
